# 微信授权保存与掉线自动重连

本 Fork 基于 `liyangpengs/qq-farm-bot`，在现有微信扫码登录基础上增加自动重连。流程参考 `Aoluis1005/QQ-farm-BOT-GO` 的应用宝授权刷新与连接恢复设计；使用本项目已有的 Node.js 微信协议实现，无需运行 Go 服务。原生微信扫码无需第三方换 Code 服务，同时保留可选的第三方应用宝登录入口。

## 使用

1. 部署本 Fork，沿用原数据目录；升级前先停服务并备份完整数据目录或 Docker 数据卷。
2. 已有微信账号需要在面板重新扫码一次。旧版本只保存登录 Code，无法从旧 Code 还原刷新授权。
3. 原生微信扫码默认开启、首次等待 **3 分钟**、最多 **3 次**；第三方应用宝登录默认开启、**5 分钟 / 3 次**。扫码/添加弹窗和账号卡片均可修改。
4. 每 **30 秒**扫描一次。普通断线在扫描首次发现时记录离线时间，等配置的分钟数后换 Code 重连；被踢下线在事件发生时记录离线时间。首次延迟结束后，若仍失败，后续每轮 30 秒扫描继续尝试——这与 Go 的实际实现一致，并非指数退避。
5. **成功重连不清零次数**。普通重连达到上限后停止，并清掉计数供界面显示停止态；手动立即重连、手动启动/停止、保存配置会重置计数。立即重连不消耗自动重连次数。
6. 游戏业务请求超时会关闭死连接并标记为超时型，此类重连**不计次数上限**，一直尝试直至恢复。Heartbeat、ACE 上报、离开好友农场的 Leave 请求按 Go 的例外处理，不使用这一业务请求超时策略。心跳自身仍沿用上游的独立健康检查。
7. 被其他设备登录挤下线时，开启自动重连按配置等待；**即使关闭定时重连，挤下线仍尝试立即换 Code 恢复**，与 Go 的 `onKick` 特殊分支一致。要明确停止账号，请点击账号“停止”按钮，待执行及刷新中的旧请求都不能再拉起该账号。
8. 换 Code 暂时失败时按 Go 规则尝试已保存 Code，连接失败再按次数限制重试。微信授权失效或第三方 Token 被拒绝时提示重新扫码/检查接口授权，失败响应和凭据不会写入日志。
9. 返回封禁/权限不足错误 `1000016` 时**持久关闭**自动重连，避免进程重启后继续无效重试。重新开启须主动保存配置。
10. 账号卡片提供重连设置、立即重连、刷新授权、连接状态、次数、超时豁免及下次检查时间；账号管理还可批量刷新微信授权。刷新授权本身不会重启在线游戏会话。
11. 第三方应用宝与本机扫码使用独立授权：保存接口地址、APITOKEN、OPENID，调用 `/api/open/v1/farm/code` 获取新 Code，兼容 Go 使用的多种响应信封。不会把第三方账号错误地交给本机扫码链路。
12. 掉线提醒按账号以 10 分钟默认窗口去重，重连恢复不受掉线提醒限流；仅在此前记录了离线时发送恢复提醒。两类通知接入现有项目通知配置，沿用已设置的渠道（包含 MeoW/Bark 等），不会导入 Go 项目的管理员密码或用户数据。

QQ 账号与外部手动 Code 不会自动获得微信授权。修改为外部 Code、切换平台或删除账号会移除旧授权绑定；普通备注修改保留授权。新的扫码授权与旧刷新请求竞争时，以新扫码为准。

## 与 Go 的核对点

| 微信账号能力 | 本 Fork 行为 |
| --- | --- |
| 扫码、授权保存、刷新凭据、获取 Code | Node 原生实现，沿用上游扫码入口 |
| 第三方应用宝登录与按账号重连 | 独立加密保存，默认 5 分钟 / 3 次 |
| 默认参数和账号独立修改 | 原生 3 分钟 / 3 次，保存后重置运行计数 |
| 扫描间隔、成功保留计数、超时豁免 | 对齐 Go 的实际调度和计数行为 |
| 被挤下线、换 Code 失败回退、受限停用 | 保留对应恢复分支 |
| 立即重连、授权状态、刷新/批量刷新 | 账号卡片与账号管理入口 |
| 恢复挂机、掉线与恢复通知 | 恢复原账号配置，接现有通知渠道 |
| 多请求同时登录 | 每账号单飞，手动停止/删除/重新扫码优先 |

## 数据与备份

授权与普通账号数据分开保存在运行数据目录：

- `wx-authorization.enc`：AES-256-GCM 加密的授权记录与开关。
- `wx-authorization.key`：本实例的本地加密密钥。

两个文件都需要随整个数据目录备份和迁移。Linux 下创建权限为 `0600`；Windows 由数据目录的 ACL 控制访问。密钥与密文同机保存，用于避免凭据以明文混入常规 JSON、接口和日志，不能抵御整个数据目录被读取。两个文件均位于 Git 忽略的 `core/data/`，不得提交到仓库。

扫码授权仅通过服务端临时映射绑定到该次 Code，不向浏览器返回 access/refresh token。刷新时先保存轮换后的 token，再请求新登录 Code，避免后一步网络失败丢失最新授权。数据损坏时不静默覆盖文件，应从完整备份恢复。

## 与上游保持同步（CMD）

本 Fork 保留完整上游提交历史。`origin` 指向本仓库，`upstream` 指向原项目。克隆本仓库后首次执行：

```cmd
git remote add upstream https://github.com/liyangpengs/qq-farm-bot.git
```

每次同步前确认工作区干净，并在独立分支合并，避免未验证的上游改动直接进入部署分支：

```cmd
git switch master
git pull --ff-only origin master
git bundle create ..\qq-farm-before-sync.bundle --all
git fetch upstream master
git switch -c sync-upstream-YYYYMMDD
git merge --no-edit upstream/master
pnpm install --frozen-lockfile
pnpm -C core test
pnpm typecheck:web
pnpm build
git push -u origin sync-upstream-YYYYMMDD
```

将日期替换为当日日期，备份文件也建议带日期。通过测试后在**自己的 Fork** 创建并合并 PR；发生冲突时保留重连接入点，再测试。不要用覆盖式同步或 `reset --hard upstream/master`，那会丢掉定制功能。本项目 CI 会对 push 和 PR 执行后端测试、前端类型检查及构建。

新增核心逻辑集中在 `credentials.ts`、`authorization-store.ts`、`wx-reconnect.ts`；上游接入点为微信扫码、账号保存/删除、Worker 生命周期及账号卡片。

## 验证范围

自动化测试覆盖加密持久化、授权绑定与删除、正确刷新协议字段、token 轮换、掉线恢复、退避上限、手动停止竞态、删除/重新扫码竞态，以及 Worker 事件接入。构建及模拟测试不代表真实微信服务验证成功；部署后还需用实际账号扫码，并观察一次实际断线后的恢复日志。
